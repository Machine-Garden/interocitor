Why it exists

Private exchange should not require a readable backend.

Most apps treat sync as a reason to hand secrets to the server. Interocitor changes the shape: devices hold the useful copy, clients seal the package, and storage carries it without becoming the place secrets live.

01

Make the best breach smaller.

If a relay is dumped, the useful payload is still encrypted. Attackers can learn metadata, not casually read the records.

02

Make secure sharing feel normal.

Users keep using the app while Interocitor handles the sealed handoff between trusted devices.

03

Use the storage that fits the secret.

A recipe vault can use Drive. A document processor can use R2. A product roadmap can use your own relay.

04

Give auditors a concrete boundary.

The answer is not "trust us." The answer is where plaintext exists, where keys live, and what the relay can still observe.

The useful claim is narrow and strong: exchange sensitive records and files through the cloud without making the cloud a reader.

This is not a hosted backend, a policy framework, or a magic privacy badge. It is safe data exchange for teams that want ordinary product code and a trust boundary they can explain.

Use it for

Different secrets. Same exchange model.

The vibe is simple: if the content matters, seal it before it moves. Public deployment, private deployment, user-owned storage, company-owned bucket - the payload boundary stays the same.

Family cookbook

Secret document processing

Stealth startup tracker

Public or private deployment

Run on public edge infrastructure or inside your own account. The important line is payload custody, not where the relay lives.

Exchange surface

One privacy rule for the whole payload.

Useful secrets are rarely one shape. Interocitor exchanges structured records and durable files under the same custody rule: readable on trusted devices, sealed everywhere else.

Structured stateRows that merge

Records that can merge.

Use tables for state that should converge across devices: tasks, cases, notes, metadata, settings, and collaboration status.

  • Local reads and writes before network sync.
  • Typed schemas, live queries, and per-column conflict resolution.
  • Encrypted changes and snapshots on the relay.
Durable bytesFiles

Files that stay exact.

Use file paths for payloads that should exist exactly as uploaded until overwritten or deleted: PDFs, images, exports, and attachments.

  • Path-addressed encrypted blobs in the same mesh.
  • Browser image helpers for Blob, File, bytes, data URLs, and SVG strings.
  • File metadata without pretending bytes are mergeable rows.

Relay choice

The server can be useful without being trusted.

Interocitor treats remote storage as a mailbox. It can authenticate devices, enforce quota, store ciphertext, route changes, and delete objects. It does not need to query, index, train on, or understand application plaintext.

WebDAV Use commodity storage for a personal or self-hosted sync space.
Google Drive Let user-owned cloud storage carry encrypted app packages.
Cloudflare Use D1 for sync metadata, R2 for file bodies, Workers for policy, and optional realtime invalidation.
Custom adapter Bring a storage contract that fits your product, compliance, or deployment shape.

Many spaces. Many endpoints. One app model.

A product can keep personal, family, work, and project meshes separate. Each can point at a different relay and use different key material, while the app keeps the same local-first API.

That is the advertisement-level reason: storage becomes replaceable infrastructure, not the place your product promise is trapped.

Security boundary

Honest privacy beats vague privacy.

Interocitor is strongest when the product is explicit about custody. With a non-null key source, row data and file bodies are encrypted before they leave the device. The relay still sees operational metadata, and a compromised device can read what that device can read.

Protected from the relay

Payload contents

Application row contents, encrypted change files, encrypted snapshots, and encrypted file bodies are not plaintext on remote storage.

  • Field names and values inside encrypted objects
  • Durable file contents
  • AES-GCM authenticated entries
Still visible

Routing metadata

The remote can still observe enough to operate the mailbox. Products should design with that leakage in mind.

  • Object names and sizes
  • Timing and device activity
  • Manifest and routing metadata
Out of scope

Compromised endpoints

The local store on a trusted device holds usable data. Device security, key recovery, and re-keying remain product responsibilities.

  • Malicious code on the device
  • Lost key material
  • Cryptographic revocation without re-keying

Start

Build the exchange. Keep the secret.

The application code stays direct: create the engine, choose local storage, choose the relay, then move records and files without making that relay a reader.

exchange shapereal public APIs
# install the client surface
yarn add @interocitor/core @interocitor/web

import { Interocitor, PortablePassphraseKeySource } from '@interocitor/core';
import { IndexedDbLocalStore, createWebCredentialStore } from '@interocitor/web';

const db = new Interocitor(adapter, {
  dbName: 'case-vault',
  remotePath: '/CaseVault',
  schema,
  localStore: new IndexedDbLocalStore('case-vault'),
  keySource: new PortablePassphraseKeySource({
    portableKey,
    credentialStore: createWebCredentialStore('case-vault'),
  }),
});

await db.init();     // trusted device is ready
await db.connect();  // encrypted sync starts

await db.table('cases').add({ title: 'Contract review' });
await db.putFile('evidence/contract.pdf', pdfBytes, 'application/pdf');

What to decide first

Interocitor gives you the safe exchange path. Your product still chooses the trust experience around it.

  1. Which users or devices should share a mesh?
  2. Where should each mesh store sealed sync objects?
  3. How will users restore or derive key material?
  4. What relay metadata is acceptable for your use case?

Interocitor · private app data without server custody

Stop building privacy on top of trusted servers.

The first rule of keeping secrets is simple: do not give them to systems that do not need them. Interocitor gives your app a Dexie-like local database, then turns sync into a personal micro data cloud: many endpoints, many keys, all orchestrated by the client.

Old shape

Privacy depends on the server behaving forever.

fragile
  1. 1User creates a secret.A note, file, case, message, record, or private workflow.
  2. 2App sends it to the backend.The database, logs, workers, search, analytics, and vendors can now touch plaintext.
  3. 3Privacy becomes a promise.Now you need policies, permissions, audits, breach comms, and perfect behaviour forever.

Failure mode: one readable server-side copy creates the breach, the leak, and the apology.

Interocitor flips this

New shape

Your devices orchestrate the cloud.

sealed
  1. 1The app uses local data.Reads, writes, live queries, rows, and files happen on the device first.
  2. 2The device locks before sync.Only encrypted packages cross the network boundary.
  3. 3Trusted devices open and merge.One app can sync through Drive, WebDAV, Workers, or your own relay. Each endpoint can have its own key.

Privacy claim: remove custody before anyone has to explain it.

The server is still useful. It syncs. It stores. It routes. It just never becomes the place where your users’ secrets are readable — or the only place your app can sync through.

Why it exists

The apology script is part of the architecture.

Once a server has plaintext, privacy becomes a behaviour promise. When that promise fails, the response is predictable: deny the exposure, blame the user, then describe the company as the victim. The clean fix is not a better statement. It is removing server custody.

Deny

“We never sell your personal data.”

The technical system still collects, shares, indexes, logs, analyses, or trains on readable data. The wording changes faster than the architecture.

Attack

“This was caused by user behaviour.”

Weak passwords, reused credentials, misconfigured settings. Sometimes true. Still not an answer to why the service held readable secrets in the first place.

Reverse

“We were the target of a sophisticated attack.”

The company that accumulated the plaintext becomes the injured party. The user becomes an incident in someone else’s postmortem.

Stop creating the apology.

If the server never gets a readable copy, there is no readable copy for attackers, vendors, operators, logs, analytics, or future business models to inherit.

This is the useful claim: not “we promise to behave,” but “our infrastructure cannot read the payload.” Interocitor moves the trust boundary to the client: local data on devices, sealed packages in storage, explicit metadata leakage, and no hidden plaintext database behind the curtain.

How it works

The client runs the cloud.

Interocitor is not a hosted backend asking for trust. It gives the app a local data layer, then lets the client sync sealed updates through as many endpoints as the product needs. Each endpoint can have its own key. No endpoint has to become the source of truth.

1Use data locallyThe app reads and writes on the user’s device first, so it remains usable offline.
2Lock before uploadUpdates and files are sealed before they touch the relay.
3Move sealed packagesDrive, WebDAV, Workers, R2, or your adapter can carry encrypted objects. The relay never receives application plaintext.
4Use different endpointsA personal vault can sync to one place; a work vault can sync to another. Keys and routes stay client-managed.
5Trusted devices catch upDevices with the right key unlock incoming changes and merge them into the local view.
Personal micro data cloud: the client can maintain several sealed sync spaces at once — personal, family, work, case, project — each pointed at a different storage endpoint and protected by a different key. The server does not coordinate identity, merge policy, or trust. The client does.
Use it forApps where trust is the product: family vaults, private workspaces, encrypted research notes, case files, document tools, personal CRMs.
Skip it forProducts that need the server to read everyone’s data, search across plaintext, own every conflict, or cryptographically revoke a keyed device without re-keying.
Access modelBasic auth can still protect the relay and block future access. The key controls whether copied data can be read. Revoke a device from the network with auth; revoke its cryptographic access by re-keying.
Storage modelStorage should be replaceable plumbing, not a privileged copy of your users’ lives. A single app can use several endpoints, each with its own key and policy.
Honest leakObject names, object sizes, timing, routing metadata, and device activity patterns can still leak to the relay.

API surface

The app still gets a normal database-shaped API.

The closest mental model is Dexie: local tables, local writes, and live queries. Interocitor aims for that same app shape, but makes rows and files private before they sync.

Closest existing reference: Dexie. Dexie makes IndexedDB feel like an application database: tables, queries, transactions, and reactive UI. Interocitor keeps that “client has a real database” idea, then adds sealed files, encrypted sync packages, and client-managed endpoints so the sync layer does not need custody.

Bring up the local database first. Start sync after the app is usable.

import { Interocitor, PortablePassphraseKeySource } from '@interocitor/core';
import { IndexedDbLocalStore, createWebCredentialStore } from '@interocitor/web';

const db = new Interocitor(adapter, {
  dbName: 'case-vault',
  remotePath: '/CaseVault',
  schema,
  localStore: new IndexedDbLocalStore('case-vault'),
  keySource: new PortablePassphraseKeySource({
    portableKey,
    credentialStore: createWebCredentialStore('case-vault', {
      storage: 'sessionStorage',
    }),
  }),
});

await db.init();     // usable offline
await db.connect();  // encrypted sync starts

Rows behave like normal typed records. The merge rules stay below the application layer.

const cases = db.table('cases');

const id = await cases.add({
  title: 'Vendor contract review',
  status: 'open',
  priority: 'high',
  updatedAt: new Date().toISOString(),
});

await cases.update(id, { status: 'reviewed' });

cases
  .query(q => q.where('status').equals('open'))
  .subscribe(rows => renderInbox(rows));

React components subscribe to database results. They do not manually maintain a shadow state graph.

import { useLiveQuery } from '@interocitor/react';

export function OpenCases() {
  const openCases = useLiveQuery(db, q =>
    q.table('cases')
      .where('status').equals('open')
      .orderBy('updatedAt', 'desc')
  );

  return openCases.map(caseRow => (
    <CaseCard
      key={caseRow.id}
      caseRow={caseRow}
      onClose={() => db.table('cases').update(caseRow.id, { status: 'closed' })}
    />
  ));
}

Files use application paths and the same privacy boundary as rows.

const evidencePath = `evidence/${caseId}/contract.pdf`;

await db.files.put(evidencePath, pdfBlob);

await db.table('caseDocuments').add({
  caseId,
  path: evidencePath,
  mimeType: 'application/pdf',
  uploadedAt: new Date().toISOString(),
});

const objectUrl = await db.files.objectUrl(evidencePath);

Trust boundary

Private does not mean magical. It means the boundary is explicit.

The promise is narrow enough to be useful: storage does not receive plaintext and does not hold the key. Metadata, timing, and device compromise still need honest product design.

Protected

  • Row contents and table fields
  • File bodies, images, PDFs, and exports
  • Encrypted snapshots and sync objects
  • Application data from the relay operator

Still visible

  • Object names unless you design around them
  • Object sizes and update frequency
  • Routing, timing, and access metadata
  • Which devices are active

Out of scope

  • Malicious code running on the device
  • Cryptographic revocation after a device has copied the key, unless the mesh is re-keyed
  • Basic auth can block future relay access, but it cannot make an old key forget old ciphertext
  • Server-side search over plaintext
  • Recovery after losing every key copy

Selection guide

Use it when local-first is right, but Dexie alone is not private enough.

Interocitor is for products that want the Dexie-style local database feel, but cannot accept a trusted sync server. It is the wrong tool when the server needs to inspect, rank, mine, or own the data.

Good fit

  • Dexie-like local apps that need private sync across devices or workspaces.
  • Private workspaces where every trusted device can hold the dataset.
  • Apps built around rows plus attachments: documents, notes, records, tasks, evidence, personal data vaults.
  • Products where “we cannot read your data” is a hard requirement, not a marketing line.
  • Small teams, families, professionals, or local-first tools that can tolerate key-custody UX.

Wrong tool

  • You need server-side analytics or search across everyone’s plaintext.
  • The server must be the final authority for every conflict.
  • The dataset is too large to sync to each device in the mesh.
  • You need one-click cryptographic revocation for a device that already possesses the key. Basic auth can stop future sync, not decryptability of data already copied.

Start building

Keep secrets local. Ship sync anyway.

Start with the promise: the server should be useful without becoming trusted. Then decide which endpoints each vault uses, how users pair devices, how keys are recovered, and what the relay can still observe.

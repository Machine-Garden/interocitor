Sheet 00 · an isolated, secure building block

The actually private database.

Everything claims to be secure. Here, privacy is a property, not a promise: your data is sealed on the device, only ciphertext crosses storage you control, and the key is the access control — no key, no data, the server included. To your code it stays an ordinary typed database — db.table('todos').add(...), live queries, merging across every device. Multiple users are the expected case.

Sheet 01 · components

What is this, actually?

A library with two first-class data surfaces. Each reads and writes on the device instantly and travels encrypted between devices:

Component · rows

A typed CRDT database

Tables, live queries, schema inference, per-column conflict resolution. State that should converge across devices — and does, deterministically, without a server adjudicating merges.

Component · files

A durable encrypted file store

Images, PDFs, exports — addressed by app paths, encrypted like rows. Files don't merge and don't compact; they exist exactly as uploaded until overwritten or deleted.

Between devices sits a mailbox, not a database: any dumb storage you already control — WebDAV, Google Drive, a Cloudflare Worker. It forwards envelopes it cannot open. The bench below runs that exact seal step in your browser — edit the row and watch what the relay would store.

Sheet 02 · legend

Why is trusting this not crazy?

Because none of it is novel cryptography. Interocitor is assembled from primitives auditors already know how to evaluate — and it writes down exactly where the boundary sits, including the parts that leak.

AES-256-GCMCRDTsWebAuthn largeBlobIndexedDBdumb storage as transport
Legend · what crosses the boundary

Protected

  • ■Row contents and table fields
  • ■File bodies and images
  • ■Encrypted sync snapshots

Visible to the relay

  • ◑Object names and sizes
  • ◑Timing and routing metadata
  • ◑Device activity patterns

Out of scope

  • ✕A hosted backend
  • ✕Server-authoritative conflict resolution
  • ✕Per-device revocation without a new mesh key
  • ✕Malicious code on the device itself

A security page that lists what leaks is worth ten that don't. The full boundary — key custody options, pairing, shared-key scenarios — is specified in the security model and shared key scenarios.

Key custody is a choice you make, not a default you inherit: memory, session, browser storage, passkey (WebAuthn largeBlob), or an encrypted envelope unwrapped by biometrics. Restore and pairing are explicit protocols — no hidden account magic.

Sheet 03 · assembly

What do I get to skip?

The infrastructure a synced app normally demands:

  • ✕A plaintext application database · the relay stores ciphertext
  • ✕A media pipeline for user uploads · files are encrypted durable objects
  • ✕A merge-arbitration backend · devices converge by CRDT rules
  • ✕An auth service · key custody is the access control
Detail · initialisationn.t.s.
yarn add @interocitor/core @interocitor/web
// Reads and writes never wait for the network.
import { Interocitor, PortablePassphraseKeySource } from '@interocitor/core';
import { IndexedDbLocalStore, createWebCredentialStore } from '@interocitor/web';

const db = new Interocitor(adapter, {
  dbName: 'case-vault',
  remotePath: '/CaseVault',
  schema,
  localStore: new IndexedDbLocalStore('case-vault'),
  keySource: new PortablePassphraseKeySource({
    portableKey,
    credentialStore: createWebCredentialStore('case-vault', { storage: 'sessionStorage' }),
  }),
});

await db.init();     // app is usable here, offline included
await db.connect();  // sync starts in the background

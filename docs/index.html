Why it exists

The strange power is choosing not to have power.

Normal databases are good. Central truth, rich queries, dashboards, and admin visibility are useful powers. Interocitor is the other bargain: surrender readable custody, then build products where private data can still move.

01

Use the cloud as a place.

Google Drive, WebDAV, R2, or your own backend can carry sealed data without becoming the readable owner.

02

Let trusted devices know.

The app works locally first. Sync is how trusted devices catch up, not a reason to centralize plaintext.

03

Give the backend boring jobs.

Store, route, quota, authorize, delete. Useful powers, none of which require reading the private data.

04

Make the privacy story concrete.

The promise is not vibes. It is where plaintext exists, where keys live, and what storage can still observe.

The server still gets a job. It just does not get the secret.

This is not less architecture. It is a different shape: a small private cloud per owner, with readable truth kept at the edge.

The switch

The old shape creates apology. The new shape changes the blast radius.

This is not Interocitor apologizing for itself. It is the reason to choose a different custody shape before the incident report exists.

The old shape

Plaintext reaches the server. Now privacy is a behavior promise.

Normal backends are powerful because they can see. When that power leaks, the apology script starts sounding familiar.

Deny "No customer data was exposed."
Attack "The user misconfigured access."
Reverse "We are the victim too."
The new shape

Storage carries the work. Trusted devices keep the readable truth.

Interocitor moves records and files through storage that cannot read the payload. The server still has useful jobs, just not the secret.

  • Store, route, quota, authorize, and delete encrypted objects.
  • Let trusted devices read, merge, and recover local app state.
  • Turn a database dump into ciphertext and operational metadata.

Use it for

Private things people actually care about.

The value is not a protocol. The value is letting apps handle sensitive everyday data without turning storage into a readable archive.

Family cookbook

Keep grandma's secret sauce in a shared recipe app. Store it in Google Drive. Do not give Google Drive the recipe.

Secret document processing

Encrypt documents aggressively, upload sealed files to your own R2 bucket, and let the Worker enforce policy without reading them.

Stealth startup tracker

Keep the roadmap, investor notes, tasks, bugs, and half-formed strategy yours while the team stays in sync.

Public or private deployment

Run on public edge infrastructure or inside your own account. The important line is who can read the data.

Compared to

The tools people reach for first.

Firebase, Supabase, PlanetScale, Dexie, iCloud, and Drive all work. Use them when a hosted database, platform cloud, or local browser store is the right shape. Interocitor is a narrower, stranger celebration of restraint: a private data world for each user, family, team, or workspace.

What is wrong with the normal stack? Nothing. It is good software for a different trust shape.
Is Interocitor a better database? No. It trades away most database conveniences for a different kind of power.
So why use it? Because sometimes the product is not a shared backend. It is a private data server per owner.

Welcome to private microclouds.

A personal personal data server: not AT Protocol, not a public data network, not one giant database everyone rents. A small encrypted app cloud per owner, running through WebDAV, Drive, R2, or storage they choose.

Data

Rows, notes, images, PDFs, and whatever your app keeps.

Private app data is not just rows in a database. It is structured state plus the files people attach to it. Interocitor keeps both under the same rule: readable on trusted devices, sealed everywhere else.

Structured stateRows that merge

Records that can converge.

Use tables for app state people expect everywhere: recipes, notes, task lists, case metadata, settings, and collaboration status.

  • Local reads and writes before network sync.
  • Typed schemas, live queries, and per-column conflict resolution.
  • Encrypted changes and snapshots in remote storage.
Durable bytesFiles

Files that stay exact.

Use file paths for bytes that should exist exactly as uploaded until overwritten or deleted: PDFs, images, exports, and attachments.

  • Path-addressed encrypted blobs in the same mesh.
  • Browser helpers for Blob, File, bytes, data URLs, and SVG strings.
  • File metadata without pretending bytes are mergeable rows.

Clouds

Your personal cloud is already waiting. Own it.

Use the storage your product, user, or deployment already trusts. Interocitor lets that storage hold encrypted app data without becoming the place where secrets are readable.

Google Drive Let users keep app data in the cloud account they already understand.
WebDAV Use a NAS, home server, or commodity hosted folder for private apps.
Cloudflare Use Workers and R2 for policy, quota, durability, and storage without readable files.
Custom adapter Bring the storage contract that fits your customer, compliance, or deployment reality.

The cloud can be useful without being trusted with the contents.

A public Worker, a private bucket, and a user Drive can all be reasonable when storage only receives encrypted data.

Infrastructure becomes a place to put things, not the place your privacy promise gets trapped.

Security boundary

Honest privacy beats vague privacy.

Interocitor is strongest when the product is explicit about custody. With a non-null key source, row data and file bodies are encrypted before they leave the device. Storage cannot read contents, but it still sees operational metadata.

Protected from storage

Data contents

Application row contents, encrypted change files, encrypted snapshots, and encrypted file bodies are not plaintext on remote storage.

  • Field names and values inside encrypted objects
  • Durable file contents
  • AES-GCM authenticated entries
Still visible

Routing metadata

Storage can still observe enough to do its job. Products should design with that leakage in mind.

  • Object names and sizes
  • Timing and device activity
  • Manifest and routing metadata
Out of scope

Compromised endpoints

The local store on a trusted device holds usable data. Device security, key recovery, and re-keying remain product responsibilities.

  • Malicious code on the device
  • Lost key material
  • Cryptographic revocation without re-keying

Start

Build the private app people actually wanted.

Start with the user's need, then choose where encrypted data lives and how trusted devices get access.

For personal software

Let the user bring their own cloud. The app stays local-first; Drive, WebDAV, or another adapter stores ciphertext for their trusted devices.

  1. Pick a storage account the user already owns.
  2. Keep readable data on trusted devices.
  3. Store only encrypted records and files remotely.

For product teams

Use Cloudflare or your own backend for policy, quota, auth, and durability without making it a reader.

  1. Decide which users or devices share a mesh.
  2. Decide how users restore or derive keys.
  3. Decide which storage metadata is acceptable.

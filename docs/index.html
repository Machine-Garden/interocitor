Data infrastructure for browser apps

Let trusted devices share app data without handing plaintext to the remote.

Interocitor combines typed, local-first CRDT rows with durable remote files. Apps work against local row state, sync changes across trusted devices, and store exact documents or media through Google Drive, WebDAV, Cloudflare Workers, or an adapter you own. Supply a client-held key source and both surfaces are encrypted before upload.

Why Interocitor

Local-first behavior and remote durability belong in the same app.

Interocitor is for teams building browser apps whose users need responsive local work, continuity across trusted devices, and durable files—without making server-side plaintext access a product requirement.

Responsive by default

Keep row work moving locally

Reads and writes use local state. Changes enter an outbox and sync when transport returns, so record work does not wait on the network.

Shared structured state

Converge across trusted devices

Typed tables and per-column conflict rules merge independent row changes into the same local view.

Durable bytes

Preserve files as files

Documents, images, and other bytes remain path-addressed remote objects. File reads return the stored object; files never enter CRDT merge.

Infrastructure choice

Choose the remote boundary

Use Google Drive, WebDAV, Cloudflare Workers, or your own adapter. With a key source, row artifacts and file bodies are encrypted before that boundary.

The app data model

Records that converge. Files that stay exact.

Both surfaces belong to the same mesh: the same devices, key source, adapters, and backend policy.

Structured state

Typed CRDT rows

Tables, schemas, local queries, per-column conflict resolution, snapshots, and deterministic convergence.

  • Local writes land immediately
  • Changes merge across devices
  • Old change logs can compact

Durable bytes

Path-addressed files

Encrypted blobs and images with put, get, overwrite, delete, metadata, and browser display helpers.

  • Bytes remain exact until replaced
  • Files do not enter CRDT merge
  • File calls require remote transport

One isolation boundary

The mesh

A mesh is the shared application data world. Its address selects the remote namespace; its credentials let trusted devices decrypt its payloads.

  • UUID or stable named address
  • Shared rows and files
  • Application-owned access policy

How it works

The remote carries row artifacts and durable files—not plaintext app state.

Rows live locally and converge through mailbox artifacts. File bodies live as direct remote objects. Decryption stays on trusted devices.

  1. 01

    Write rows locally

    Row reads and writes use the local store. CRDT changes enter an outbox, so row work continues offline.

  2. 02

    Transfer files directly

    File put, get, and delete calls use the remote adapter immediately. They are not queued in the row outbox.

  3. 03

    Encrypt before upload

    With a non-null key source, row changes, snapshots, and file bodies are encrypted before they cross the adapter boundary.

  4. 04

    Converge rows, read exact files

    Trusted devices decrypt and merge row changes locally. File reads return the stored object without CRDT merge.

For a protected mesh, a D1 export exposes encrypted row-sync artifacts and operational metadata; an R2 export exposes encrypted file bodies and object metadata. Neither includes readable payloads. Availability is separate: a malicious remote can still drop, withhold, or roll back data.

Security boundary

Private means naming the boundary, including what remains visible.

A non-null key source protects remote payload contents. It does not hide every signal, make endpoints trustworthy, or turn an unreliable remote into a reliable one.

Request authorization

The host controls which requests reach a mesh namespace.

Address validation, authentication, authorization, audit, and administrative policy belong to the application hosting the remote.

Decryption authority

The portable key remains a separate capability.

Anyone with both the portable key and a copy of the remote artifacts can decrypt protected payloads, even if the original host rejects their requests.
